# CLAUDE.md

Guidance for working in this repository.

## What this is

HouseBridge is a native macOS (15+) menu bar app and CLI, written in Swift 6 with no third-party packages and no VM. It does three jobs:

1. **Rule engine.** Lutron Caseta Pico remotes/switches and UniFi Protect cameras/sensors trigger Philips Hue lights, scenes and rooms. All behavior lives in one YAML file (`~/.config/housebridge/config.yaml`, or `$HOUSEBRIDGE_HOME`).
2. **HomeKit bridge (for UniFi Protect).** Publishes Protect motion, contact, leak and doorbell sensors to Apple Home so it can replace Homebridge's UniFi Protect plugin. Cameras can also appear as HomeKit cameras with snapshots and live view (opt-in `cameras: true`); no HomeKit Secure Video.
3. **Sensor readings and alarms.** Temperature/humidity from UniFi Protect environmental sensors (read directly) and smoke/CO alarms plus readings from HomeKit-only accessories such as an Owl smoke detector (through a hidden Mac Catalyst helper inside the app), shown in the window and usable as rule triggers. See "Home sensors" below.

README.md is the user-facing doc; this file is for working on the code.

## Commands

```sh
swift build --disable-sandbox              # debug build: housebridgectl + HouseBridgeMenu
swift build -c release --disable-sandbox   # release build (SRP math is ~50x faster than debug)
swift test --disable-sandbox               # all tests; ~60 s, almost all of it SRP bignum math in a debug build
swift test --disable-sandbox --filter HAPProtocolTests   # one suite
./scripts/bundle.sh                        # universal HouseBridge.app (+ .zip) with the HomeKit helper embedded
SKIP_HOMEKIT_HELPER=1 ./scripts/bundle.sh  # same, without the helper (no Xcode account needed)
./scripts/build-homekit-helper.sh [--no-copy]   # just the helper (Xcode, automatic signing); --no-copy leaves it in .build/
./scripts/build-probe.sh                   # HouseBridgeProbe.app: dumps every HomeKit accessory/characteristic to stdout
python3 -I scripts/survey-sensors.py [--skip-homekit|--skip-protect]   # read-only sensor survey of one house (Protect directly + HomeKit)
```

Always pass `--disable-sandbox` to `swift build`/`swift test`.

CLI (`housebridgectl`): `init`, `validate`, `run [--dry-run]`, `events`, `devices`, `list lutron|hue|unifi`, `diagnose`, `logs`, `pair-hue`, `set-unifi-password`, `homekit [--reset]`, `import-homebridge`. Global `--config <path>` picks another config file.

Use `HOUSEBRIDGE_HOME=/tmp/somewhere` to run the CLI against an isolated config/state directory when experimenting.

## Layout

- `Sources/HouseBridgeCore/` – everything that matters
  - `Config.swift`, `YAML.swift` – hand-written YAML subset parser and config validation (`ConfigLoader`)
  - `Hub.swift` – wires sources (Lutron, UniFi, HomeKit) to the rule engine and Hue; one Hub per loaded config. `buttons:` (momentary Home.app buttons): `ConfigLoader.parseButton` makes each a `Rule` with `homekitButton` set and a trigger no event can match, published like a `homekit_switch` (`Config.homekitSwitches`); a write of On goes to `RuleEngine.pressButton` (= `runNow`: ignores presence holds, stamps `manualAt`), and `Hub` flips the switch back off after 1 s. Names must be unique across buttons and `homekit_switch`es. Not seen in Home.app yet
  - `RuleEngine.swift`, `Events.swift` – `TriggerEvent` (has an optional `deviceID`, the Protect id), gesture timing, cooldowns
  - `Schedule.swift` – `when: { at: … }` rules: `Sun` (NOAA sunrise/sunset), `Schedule` (clock/sunrise/sunset + offset + weekdays), `ClockScheduler` (polls the wall clock every 10 s and emits `Source.clock` events; skips times >5 min late after Mac sleep). Needs `location:` for sun times. Sun math was cross-checked against an independent Meeus bisection, not just published tables
  - Catch-up (`RuleEngine.catchUp`): edge-triggered `at:` rules miss changes when the app was down, the Mac slept or a device was unreachable. At startup (5 s after, `catchUpOnStart`), after wake (`ClockScheduler.onWake`, gap >60 s) and when a scheduled action fails (retries after 60 s/5 min/15 min, only that device), the latest due `at:` rule per device is re-applied if it is a steady state (not `off_after_seconds`, toggle, dim) and no presence hold covers it. Deliberately never on a timer, so manual changes survive. A config reload restarts the engine and so also catches up. **Not verified on a real plug/bridge**; covered by `CatchUpTests` with fakes
  - Run now (`RuleEngine.runNow`, the window's button on each Upcoming event that comes from a rule): runs the rule's actions at once (ignores trigger, `between`, cooldown, presence holds) and stamps each target device key in `manualAt` (persisted via `HoldStore` in `overrides.json`, pruned after 7 days). `catchUp` and presence `reconcile` skip a candidate whose schedule time is not after the stamp, so wake/restart/retries never undo a manual change; the next scheduled change for that device supersedes it naturally. A failed manual run withdraws its stamp and is not retried
  - Skip (`RuleEngine.skip`/`unskip`, the window's Skip button): one occurrence of a scheduled rule, keyed by `Upcoming.skipKey(rule, due time)` and persisted in `skips.json`. `fire` drops a clock event whose `schedule.previous(onOrBefore: event.date)` matches a skip (and consumes it); the rule's devices are also stamped in `manualAt` up to the skipped time so catch-up/reconcile do not apply it late or fall back to an older change. The window keeps its own `skippedKeys` for instant feedback
  - `Presence.swift` – `presence:` holds ("someone is home"): sensor triggers pause automatic rules (non-Pico) that act on listed devices for `hold_hours`, sliding; `RuleEngine` keeps `holdUntil`, persists it via `HoldStore` (`holds.json`), cancels pending Lutron off-timers when a hold starts, and on expiry `reconcile` runs, per device, the latest `at:` rule due (`Schedule.previous`) plus any `on_resume` rules
  - `Simulation.swift` – `simulate:` (looks-lived-in lights): `Simulation.plan` picks, per night, whether it is active and the random sessions (room, start, length), seeded from name+date so restarts/reloads reproduce the same night; `RuleEngine.simulate` fires them as synthetic clock rules with `off_after_seconds`, so presence holds pause them like any automatic rule. A `lights:` entry may carry `also:` (`Simulation.companions`, same index as `choices`): extra light actions in the same session, paused with it
  - `Holiday.swift` – `holidays:` (festive colors): date range + evening window (default sunset−30 to 23:00); `RuleEngine.runHolidays` emits `Action.holiday(HolidayStep)` start/end steps (`dueHolidaySteps` decides, in-memory `done` set), and `HueActions.holiday` applies them to every light with `supportsColor` (from the bridge inventory). Any active presence hold delays the start. **Not verified on a real bridge**: in particular that a color-temperature PUT on an off light leaves it off
  - `Alarm.swift` – `alarms:` (person detected while nobody is home): `RuleEngine.alarmEvent` tracks active/present/last per alarm, a countdown ends it (`keep_seconds` after the last event, `max_seconds` if a detection never ended), steps run in order through a per-alarm task chain as `Action.alarm(AlarmStep)`. `HueActions.alarm` switches on only lights that are off and remembers them, so the end switches off only those; `ShortcutRunner` runs macOS Shortcuts (`shortcuts run`, no shell) for the HomePod sound. Any presence hold blocks a start but does not stop a running alarm (door-motion cameras start holds, so they can't be alarm triggers). **Not verified**: Hue calls, the Shortcuts/HomePod playback, and what Protect's `person` events look like on a real camera
  - `Hue/HueScene.swift` – `create-scene <name> --room <room|zone> --kelvin K [--brightness] [--replace]`: POSTs a CLIP v2 scene (one action per light: on, dimming, `color_temperature.mirek`; lights without white temperature get on+brightness only); `--replace` PUTs new actions to the same-named scene. Mirek is `1e6/K`, valid 153–500. Body building and mirek are tested. **Not verified on a real bridge**: the POST/PUT payloads are from memory of the API docs
  - `Hue/LightDefaults.swift` – `light_defaults:` (default white temperature for every Hue light when on; overrides per light/zone/room, most specific wins, or `ignore`). `LightTemperatureVerifier` is the only place HouseBridge reads Hue state: every `check_seconds` (30) it GETs `/resource/light`, `/resource/scene` and `/resource/smart_scene` and PUTs the target mirek to lights that are on, in white mode (`mirek_valid`), outside any room/zone with a recalled scene (`status.active` != inactive) or an active smart scene (`state == "active"`: Natural light and other time-based scenes move the lights themselves; before this they were fought, which showed as "dims, then changes color" at the smart scene's time slot), and further than `tolerance_kelvin` off. The log line names the room and brightness (`light ‘X’ (Room, 30%): 2653 K → 3003 K`): many lights at one odd value means something recalled a setting (Hue routine, Home.app scene), not drift. `housebridgectl check-hue [name]` (`HueSchedule`) is the read-only check: scenes vs the `light_defaults` target (ok/DIFFERENT), lights (white K or COLOR MODE xy), smart scenes with their time slots, and the Hue-app routines with their times and scenes; unrecognised routine shapes are printed raw. Colored lights (`mirek_valid` false) are never touched, unless the winning override has `reset_color: true` (`LightTemperature.override(for:)`, `TemperatureCorrection.fromColor`; it sends the same mirek PUT, which Hue turns into white mode; it would fight holiday colors); a light that ignores a correction is not re-sent for 2 check periods. `LightTemperature.plan` is pure and tested. **Not verified on a real bridge**: the CLIP v2 field names (`mirek_valid`, scene `status.active`, `smart_scene` `state`/`week_timeslots`, `behavior_instance`) are from memory of the API docs
  - `Lutron/`, `Hue/`, `UniFi/` – device clients. `UniFi/ProtectClient.swift` logs in, reads the bootstrap (re-read every 5 min for sensor stats), follows the update websocket; `ProtectPacket.swift` decodes packets, `ProtectInterpreter` turns them into events and `ProtectStats` parses sensor readings
  - `Lutron/LutronPairing.swift` – `pair-lutron`: LAP pairing on port 8083 using Lutron's shared app identity (`LutronPairingAssets.swift`, copied programmatically from pylutron-caseta's assets.py; do not hand-edit), waits for the bridge button, sends a CSR made with `/usr/bin/openssl`, saves `ca/cert/key.pem`, then pings LEAP on 8081. **Not verified against a real bridge**: tests cover message building/parsing, the embedded identity loading and file modes
  - `Kasa/` – TP-Link Kasa plug output (`kasa:` config, `plug` action, `presence` pauses `plug:`). `KasaProtocol.swift`: legacy XOR over TCP 9999, or KLAP over HTTP :80 (account-hashed AES handshake; IOT or SMART JSON), auto-detected per plug. `KasaBridge` holds `off_after_seconds` timers like `LutronBridge`. A plug with `homekit: true` is published as an Outlet (`HAPLayout.build` `outlets:`, aid key `outlet:<name>`); Home.app writes go to `KasaBridge.setPlug`, `KasaBridge.onChange` plus `KasaBridge.monitor` (reads every plug each 60 s, 30 s while one is down, and turns the Kasa status red/green on change, logging each outage once) push the real state back. Hue has the same kind of loop in `Hub` (a one-request `HueClient.ping` each minute, an inventory reload every 30 s while down), and a failed write reverts the outlet. KLAP needs plain HTTP, hence `NSAllowsLocalNetworking` in `bundle.sh`. Password: Keychain service `housebridge.kasa` (`set-kasa-password`). **Not verified against a real plug (or the Outlet in Home.app)**: tests cover XOR vector, KLAP self round-trip, parsing and config only
  - `Matter/` – Matter controller (stage 1 only: pairing and a cluster dump; nothing feeds the rule engine yet). `MatterController` wraps Apple's `Matter.framework` (`MTRDeviceController` on our own fabric, as a second admin next to Apple Home); `MatterStore` keeps `matter.json` (0600: fabric root key, IPK, commissioned nodes, `MTRStorage` blobs). `pair-matter <code>` joins a device given a Home.app "Turn On Pairing Mode" code, `list matter` wildcard-reads every attribute. The Owl smoke detector turned out to be a plain HomeKit (HAP) accessory with no Matter code, so nothing consumes Matter yet. Attestation failures are logged and accepted (no PAA store). **Not verified on a real device**: the sandbox blocks UDP sockets, so `factory.start` fails there with MTR error 33554433; only the store and code parsing are tested
  - `HomeSensors/` – `home_sensors:` (UniFi Protect `stats` read directly; HomeKit accessories via the helper): `SensorStore`, `HomeSensorServer`, `HomeKitHelperLauncher`. Details in "Home sensors" below
  - `HAP/` – the HomeKit bridge (see below)
  - `Import/` – Homebridge importer (see below)
  - `Keychain.swift`, `TLS.swift` (trust-on-first-use pinning), `Diagnostics.swift`, `Catalog.swift`, `Paths.swift`
- `Sources/housebridgectl/main.swift` – CLI
- `Sources/HouseBridgeMenu/` – SwiftUI menu bar app. The menu only has Open HouseBridge and Quit; `MainWindow.swift` is the window (icon, per-subsystem status, action buttons, Upcoming Events from `Upcoming.swift` in core, activity log, and the QR code and setup code until HomeKit is paired). With `home_sensors:` it also shows a large temperature/humidity readout under the icon (red above 80°F, blue below 68°F, else green: `TemperatureBand` in core; greyed when stale) and a Sensors section sized to its rows. **Not seen running**: the agent sandbox cannot launch GUI apps, so the layout has only been compiled
- `Tests/HouseBridgeCoreTests/` – XCTest
- `Tools/` – things built outside SwiftPM with Xcode or `swiftc` because HomeKit only exists in the iOS (Mac Catalyst) SDK: `HouseBridgeHomeKit` (the sensor helper), `HouseBridgeProbe` (diagnostic dump), `HouseBridgePair` (below)

`Subsystem` is `lutron, hue, unifi, kasa, homekit, sensors`; the menu app and `Catalog` iterate `allCases`.

## HomeKit bridge (`Sources/HouseBridgeCore/HAP/`)

A from-scratch HomeKit Accessory Protocol (HAP) server. CryptoKit supplies Curve25519, Ed25519, HKDF-SHA512 and ChaCha20-Poly1305; everything else is ours.

| File | Role |
|---|---|
| `BigUInt.swift` | Minimal unsigned bignum + Montgomery modular arithmetic (no long division needed) |
| `SRPGroup.swift` | The RFC 5054 3072-bit prime (= RFC 3526 group 15). Generated and primality-checked from its π-based definition, not typed from memory; do not hand-edit |
| `SRP.swift` | SRP-6a (SHA-512, user `Pair-Setup`), server and a test-only client |
| `TLV8.swift`, `HAPCrypto.swift` | TLV8 codec; HKDF/ChaCha helpers and nonce builders |
| `HAPStore.swift` | Identity + pairings persisted in `homekit.json` (0600): device id, Ed25519 key, setup code, setup id, config number `c#`, pairings, stable accessory ids, cached device list. Only writes when something changed |
| `HAPAccessories.swift` | Accessory/service/characteristic model, `HAPLayout.build` (Protect device -> HomeKit services), layout fingerprint for `c#` |
| `HAPServer.swift` | Protocol core with no sockets: `HAPServer` (database, values, events, pairings) and `HAPConnection` (pair-setup, pair-verify, encrypted framing, `/accessories`, `/characteristics`, `/pairings`, EVENT notifications) |
| `HAPListener.swift` | `NWListener` + Bonjour `_hap._tcp` advertisement; feeds bytes to `HAPConnection` |
| `HAPCamera.swift` | Camera TLV8 blobs (supported video/audio/RTP configuration, streaming status) and the refusal answer to SetupEndpoints. Opt-in via `homekit: cameras: true`. Stage 1 = snapshots only: `HAPConnection` serves `POST /resource` asynchronously (later requests wait), `ProtectClient.snapshot` fetches the JPEG reusing the cached login. Live view is in `HAP/Camera/` (below) |
| `Camera/SRTP.swift`, `RTP.swift` | SRTP/SRTCP sender (AES-CM-128 + HMAC-SHA1-80; CommonCrypto for AES-CTR, CryptoKit for HMAC) checked against the NIST CTR vector and RFC 3711 B.3 key derivation; RTP packets; H.264 depacketizer (single/STAP-A/FU-A) and packetizer (re-fragments to the viewer's MTU, puts SPS/PPS before key frames) |
| `Camera/RTSP.swift` | SDP parser, `RTSPClient` (DESCRIBE/SETUP interleaved TCP/PLAY, keepalive) over an `RTSPTransport` (`NWRTSPTransport`: TCP or TLS with TOFU pin on "host:7441") |
| `Camera/AudioTranscoder.swift` | RFC 3640 AAC depacketizer; AAC to mono 24 kHz Opus with `AVAudioConverter` (20 ms packets, RTP clock 48 kHz so +960 per packet) |
| `Camera/CameraStream.swift` | Stream TLVs (SetupEndpoints request/response, selected configuration) and `CameraStreamManager`: sessions, ports, RTSP in, SRTP out over `MediaSocket` (UDP), RTCP sender reports every 5 s, ends when the viewer ends it, its HAP connection closes, or the camera stream drops. Factories for RTSP and sockets are injected, so tests run the whole flow with fakes |
| `HomeKitBridge.swift` | Public façade used by `Hub`: lifecycle, single-instance `flock`, inventory -> accessories, Protect events -> characteristic updates |

Mapping: camera `motion` -> MotionSensor; `ring` -> StatelessProgrammableSwitch (single press event); sensor `contact` -> ContactSensor (1 = open); `motion` -> MotionSensor; `leak` -> LeakSensor; a sensor with temperature/humidity `stats` also gets a TemperatureSensor (°C) and HumiditySensor (see "Home sensors"); with `smart_detections: true`, each smart-detect type -> an extra MotionSensor. Bridge is aid 1; each Protect device gets a permanent aid.

Wiring: `ProtectClient` takes `onInventory:` (called after every bootstrap, items carry initial `state` and sensor `measurements`) and `onReadings:` (sensor stats, live and every 5 min; `Hub` forwards them to `HomeKitBridge.updateReadings` and the `SensorStore`); `Hub` tees raw Protect events to `HomeKitBridge.handle` as well as the rule engine. In `--dry-run`/`events` modes the HomeKit bridge is not started. Only one process may own the bridge (`homekit.lock`); `Hub.stop()` releases it synchronously so a config reload can restart it.

Config (`homekit:` section): `name`, `port`, `setup_code` (validated; HomeKit rejects trivial codes), `smart_detections`, `cameras`. It requires a `unifi:` section.

### What is and is not verified

- Verified by tests: bignum against Python `pow()` vectors, Fermat on the group prime, SRP client/server round trip, TLV8, and the whole pairing/session/event flow against an in-process "controller" in `HAPProtocolTests`.
- **Not verified:** the camera services and snapshots in Home.app (the TLV layouts in `HAPCamera.swift` and `CameraStream.swift` were written from the HAP spec with no reference implementation and may need adjusting; live view has never run against a real camera or iPhone, and the RTSP/UDP network code (`NWRTSPTransport`, `NWMediaSocket`) has not run at all, since the sandbox blocks sockets), pairing with a real iPhone/Home.app, and the network layer (`HAPListener`, Bonjour). The controller in the tests is written from the same reading of the HAP spec as the server, so it proves self-consistency, not interoperability. The agent sandbox blocks opening listening sockets (`EPERM`), so the listener could not be run there; test live outside the sandbox on a real LAN.
- Known ambiguity: the SRP session key hashes the unpadded `S`; about 1 in 256 pairing attempts may fail on a leading-zero mismatch. Retrying works.
- Pairing requires the iPhone/Mac to be on the same LAN/VLAN as the bridge (Bonjour + direct TCP). It cannot be done remotely, and Home Assistant cannot either. Options: use Home.app on a Mac on that LAN, or have an edit-capable Home member pair at the house. If pairing times out, check `housebridgectl logs` (look for `pair setup started`), `dns-sd -B _hap._tcp`, the macOS firewall prompt, Local Network permission and VLAN isolation.

## Home sensors (`Sources/HouseBridgeCore/HomeSensors/`, `Tools/HouseBridgeHomeKit/`)

```yaml
home_sensors:
  devices: [Owl upstairs Master]   # HomeKit accessories, by name as in Home.app ("*" = all); needs the helper
  unifi: [USL Environmental]       # UniFi Protect sensors, read straight from the console; no helper, no Homebridge
```
At least one list is required; `unifi:` needs a `unifi:` section. Rule trigger: `when: { homekit: <name>, event: smoke|co, state: detected|clear }` (`Source.homekit`; defaults smoke/detected). `Rule.isPaused` never pauses a `.homekit` rule: presence holds must not silence a smoke alarm.

**UniFi Protect, direct.** `ProtectStats.measurements` parses `stats` (temperature °C, humidity %, light lux; `{"value": n}` or a bare number, partial updates included) from the bootstrap (`ProtectInventory.Item.measurements`), from live `sensor` updates (`ProtectInterpreter.readings`) and from a bootstrap re-read every 5 min (Protect only pushes changes). Readings go to `SensorStore.ingest(protect:)` (accessory id `unifi:<id>`, kept only for names under `unifi:`) and, for every Protect sensor, to `HomeKitBridge.updateReadings`, which publishes Temperature/Humidity services on the sensor's accessory (`HAPLayout.measurement`, `HAPValue.double`; `HAPDevice.provides` gains "temperature"/"humidity"), so Homebridge's copy can be retired. **Not verified on a real console:** the exact shape of live `stats` updates. The Bend console has one environmental sensor (USL Environmental, temp+humidity, no light), two USL Motion and an UP Sense whose mount type reads "leak" with `isOpened` null (its `contact` events may never fire; check before relying on one in a presence hold).

**HomeKit accessories, via the helper.** HomeKit cannot be loaded into a regular Mac app, so `Tools/HouseBridgeHomeKit/` is a faceless Mac Catalyst process (`LSBackgroundOnly`, no UIApplication, no scenes, no window) embedded in `HouseBridge.app/Contents/Helpers/`. It watches every `HMHome` accessory with a smoke, CO, temperature, humidity, air-quality, PM2.5, VOC or CO2 characteristic, enables notifications, re-reads everything every 5 min and smoke/CO every 30 s (in case notifications do not arrive: in an agent-sandbox run every `enableNotification` returned "Missing entitlement for API", so on a real Mac check `logs/homekit-helper.log`), and sends one JSON object per line to the Unix socket `Paths.sensorsSocket` (0600). `HomeSensorServer` (started by `Hub`) listens; a live socket already there means a second HouseBridge and it refuses. `SensorStore.ingest(line:)` (pure, tested) keeps the latest reading per accessory+kind and makes a `TriggerEvent` only when smoke/CO changes; an alarm already on at connect is reported, an unreachable sensor keeps its last alarm state. `SensorStore` reports `changed` also when the same value arrives >60 s later so the window's "updated" time moves. Not started in `--dry-run` (it would take the socket from the running app). `HouseBridgeHomeKit --list [--match words]` prints every sensor in every home with its value and whether it is already forwarded.

**Starting the helper.** `HomeKitHelperLauncher` (from `Hub`) runs `open -g -j -a` on the bundled app; if that fails (it did on PlexMacMini4, LaunchServices error -10825, while the executable itself runs fine) it runs the executable directly with output in `logs/homekit-helper.log`. It does nothing while a `HouseBridgeHomeKit` process exists, retries every 30 s while not connected, and the helper quits itself after 90 s without HouseBridge (10 min if it never connected; `--stay` disables). `HOUSEBRIDGE_HOMEKIT_HELPER` points at a helper outside the bundle.

**Window.** `Hub`'s `onSensors` callback feeds `AppModel`; `AppModel.sensorIsStale` judges Protect readings by the UniFi status (30 min) and HomeKit ones by the helper connection (15 min). The `sensors` subsystem is red while a needed helper is not connected, and then nothing watches the alarms.

**Signing and distribution (hard-won).**
- The helper needs `com.apple.developer.homekit`, so it carries a provisioning profile; every Mac that runs it must be in the profile's device list (developer portal, Devices). The profile type is "Mac Catalyst App Development", which the portal's manual profile page does not offer: let Xcode make it (`-allowProvisioningUpdates`, automatic signing, team in the project). A manual macOS App Development profile silently drops the HomeKit entitlement. The profile expires after a year.
- Bundle id is `local.housebridge.probe` for both the helper and the probe, because only that App ID has HomeKit; Xcode could not create a new App ID from the agent session ("No Accounts"). Product name is HouseBridgeHomeKit.
- `HouseBridge.app` is ad-hoc signed. `bundle.sh` must not use `codesign --deep` on it: that re-signs the helper ad-hoc and strips its HomeKit signature. The helper keeps its own signature.
- `HouseBridge.app`'s Info.plist must carry `NSHomeKitUsageDescription`. A helper started by HouseBridge has HouseBridge as its TCC "responsible process"; without the key macOS kills the helper with `__TCC_CRASHING_DUE_TO_PRIVACY_VIOLATION__` the moment it touches HomeKit (seen as a connect-then-drop loop). The Home permission prompt is for "HouseBridge".
- Mac Catalyst apps built with this SDK must either use the UIScene lifecycle or avoid UIApplication altogether; a UIApplicationMain app without scenes aborts at launch, and one with a scene opens a blank window. The helper avoids UIKit's app machinery entirely (`RunLoop.main.run()`).
- `build-homekit-helper.sh` leaves a copy of the helper in the repo root unless run with `--no-copy` (which `bundle.sh` uses); do not commit it.
- **Not verified on real hardware**: the helper was run (faceless, from the agent shell) and listed the accessories, and the Mini ran the window-based build; the full launch-from-HouseBridge path after the TCC fix, notification delivery, and the Home.app view of the published Temperature/Humidity services were not seen. Tests cover the store, config, Protect parsing, the layout and the presence exemption; the socket test skips in the agent sandbox (`bind` is blocked).
- The Owl (San Jose) exposes Temperature, Humidity, Motion, Smoke and CO plus two Owl-specific custom services, no air quality.

## Homebridge importer (`Sources/HouseBridgeCore/Import/`)

`housebridgectl import-homebridge` moves the UniFi Protect settings from a running Homebridge into the HouseBridge config.

- Finds Homebridge via Bonjour (`BonjourDiscovery`), probes the Config UI X web UI on port 8581 (`HomebridgeUIClient`: `/api/auth/settings`, `/api/auth/login` or `/noauth`, `/api/config-editor`, `/api/accessories`), or reads a file (`--from-file`) or a given `--ui` URL. Bonjour alone only reveals name/IP/port; what a bridge exposes cannot be read without pairing.
- `HomebridgeImport.parse` extracts the Protect controller (`address`, `username`, `password`) and reports everything it cannot carry over (other plugins/accessories, plugin options, Home.app automations and names). The Config UI X platform (`config`) is ignored.
- **It never overwrites a config.** `ConfigAppend.apply`: no file -> create; file exists -> append only the missing top-level `unifi:`/`homekit:` sections after verifying the existing file loads, the merged file parses and validates, and every existing section is unchanged; keeps a `config.yaml.bak-<timestamp>` copy. Sections already present are left alone; if both exist it does nothing. An existing config that does not load is refused untouched. `--out` picks another file, `--print` only prints.
- The Homebridge password is never written to YAML; `--store-password` puts it in the Keychain, otherwise use `housebridgectl set-unifi-password`.
- The Bonjour discovery and web-UI download have not been run against a live Homebridge (sandbox); the Config UI X endpoints are from memory. `--from-file` is the reliable fallback and is covered by tests.

## Conventions and gotchas

- Match the surrounding code: terse comments that explain *why*, `// MARK:` sections, no new dependencies.
- Swift language mode is v5 (`Package.swift`); several classes are `@unchecked Sendable` and rely on a single serial queue. `HAPServer`/`HAPConnection` are not thread-safe: `HomeKitBridge` and `HAPListener` share one dispatch queue, and every call into the server must happen on it.
- Secrets: the UniFi password lives in the Keychain; `Diagnostics.sanitize` masks `password`, `token`, `app_key` and `setup_code`. Never log or write secrets to YAML.
- The YAML parser rejects duplicate keys and tabs; config sections are validated with `rejectUnknown`, so new keys must be added to the allowed lists in `Config.swift`.
- Existing tests construct `ProtectInterpreter.Device(id:name:kind:)` and `TriggerEvent`; keep new fields optional/defaulted.

## HouseBridgePair (`Tools/HouseBridgePair/`, `scripts/build-pair.sh`)

macOS Home.app has no Add Accessory command. `HMAccessorySetupManager` (macOS 27+; HomeKit ships only in the iOSSupport/Catalyst SDK) can show the system sheet, so this is a tiny Mac Catalyst app built outside SwiftPM with `swiftc -target <arch>-apple-ios27.0-macabi`. Ad-hoc signed: the sheet asks for the setup code. `--use-payload --uri X-HM://…` needs the restricted `com.apple.developer.homekit.allow-setup-payload` entitlement (Developer account + profile; `build-pair.sh --sign … --profile …`).

- **Found on macOS 27.2:** in the Catalyst copy of HomeKit, `+[HMAccessorySetupManager isSupported]` is hard-wired to NO (`mov w0,#0; ret`, seen in lldb), the SDK header lists it for iOS/macOS only (not Catalyst), and `homed` here does not register the `com.apple.homed.xpc.accessory-setup` XPC service, so `performAccessorySetup` fails with NSCocoaErrorDomain 4099. The app therefore no longer gates on `isSupported`; pair from an iPhone/iPad on the LAN instead unless a later macOS fixes this. There is no native macOS HomeKit framework in the SDK.
- **Not verified:** it compiles and signs, but the agent sandbox cannot launch GUI apps, so `isSupported` and the pairing sheet have never been seen running. It must run on the same LAN as the bridge.
